## 2. 单流短上下文 · 五类负载（tok/s）

| 负载 | **LSA+DSpine（本配置）** | DSpine-only（无 LSA） | LSA 单独（无投机） |
|---|---|---|---|
| A 自由问答 | **52.4** | 52.6 | — |
| B 逐字引用 | **198.2** | 179.7 | — |
| C 代码 | 81.0 | **118.0** | — |
| D JSON | **173.4** | 161.8 | — |
| E 推理 | 113.2 | **117.7** | — |
| **均值** | **123.6** | 126.0 | 25.2 |
| accept len | 5.02 – 5.36 | 5.51 | — |

**解读**：短上下文装得进 512 token 的 dense window，稀疏省不下算力却要付选择开销，所以 LSA 只持平（B/D 更好，C/E 略差）。**LSA 的价值在长上下文**。

## 3. 长上下文

| 指标 | LSA+DSpine | DSpine-only | 比值 |
|---|---|---|---|
| decode @64k（已扣 prefill） | 90.9 tok/s | 90.5 tok/s | 1.00× |
| **decode @119k** | **94.6 tok/s** | 63.9 tok/s | **1.46×** |
| **prefill @119k** | **29.5 s（4032 tok/s）** | 41.5 s（2865 tok/s） | **1.41×** |

LSA 的 decode 速率与上下文长度基本无关（64k 90.9 → 119k 94.6），这正是稀疏注意力的设计目标。

### CUDA graph 的贡献（同代码、同机、@119k、多次重复）

| 配置 | 各次 tok/s | 中位 |
|---|---|---|
| 图关闭 | 82.78 / 81.26 / 80.12 / 81.43 | **81.35** |
| 图开启 | 93.01 / 97.79 / 97.56 / 87.69 / 94.55 | **94.55** |

→ **+15.6%**，两组测量区间不重叠。

## 4. 并发吞吐（短上下文，每级 2 轮取中位）

### 默认档（`max-mamba-cache-size 64` → 并发上限 12，KV 池 124,850）

| 并发 | tok/s | 单请求时延 |
|---|---|---|
| 1 | 87.7 | 2.92 s |
| 2 | 157.3 | 3.20 s |
| 4 | 278.5 | 3.56 s |
| 8 | 472.4 | 4.14 s |
| **12** | **495.4** | 5.88 s |

### 放宽档（mamba 96 / mem-fraction 0.78 → 上限 19，但 KV 池缩到 20,974）

| 并发 | tok/s | 时延 |
|---|---|---|
| 12 | 462.7 | 6.17 s |
| **16** | **605.6** | 6.36 s |
| 19 | 553.3 | 8.34 s |

峰值 **≈606 tok/s @ 16 并发**。1→8 近乎线性（每翻倍约 1.7×），8→12 仅 +5%，16 为峰值、19 反而下降（KV 池被挤压后开始驱逐）。

> 取舍：放宽并发是拿 KV 池换的（124,850 → 20,974 token，缩 6×）。长上下文场景应保持默认档。

## 5. 每步耗时分解（用同一 run 的 accept 扣除接受率差异）

| 上下文 | LSA+DSpine 每步 | LSA 单独（1 token/步） |
|---|---|---|
| ~168 token | **27 ms** | 39.8 ms |
| 16k | 56.8 / 58.3 ms | 41.3 / 41.8 ms |
| 64k | 59.8 / 54.5 ms | — |
| 120k | 58.8 / 55.1 ms | 43.3 ms |

两条结论：

1. LSA+DSpine 在 ≥16k 之后**步耗时完全平坦**，与上下文长度无关；
2. LSA 单独从短上下文到 100k 只涨 **8.8%**，因此「跨过 dense window 后那约 29 ms 的跳变」属于 **DSpine 侧**（草稿的全上下文注意力 + 线性重放），不属于 LSA。

## 8. 测量方法与注意事项

1. **机内噪声约 ±10–13%**，3% 以内的差异不可信。凡标注「多次 / n=4–5 / 2 轮取中位」的才是硬结论。
2. **短上下文 tok/s 受输出长度与 accept 波动影响很大**（同配置不同次可差 5–10%）。跨配置比较请优先看 **accept len** 与 **每步耗时**。
3. **长上下文基准对每次启动的 KV 预算敏感**：实测可用输入长度在 116,552 – 119,005 token 之间浮动，只有与 A/B 同期测量的数据才可比。
4. **`--decode-log-interval 1`（用于统计 accept）会拉低 tok/s 约 10–15%**，带日志与不带日志的数字不能混比。
5. 并发吞吐用固定 256 token 预算、每并发级别 2 轮、取中位；请求前缀互不相同以避开 radix 前缀缓存造成的虚高。
6. 长上下文 decode 速率用「同 prompt 先预热前缀缓存、再取第二次墙钟」的方式扣除 prefill。

## 10. 已知限制

- **FP4 精度**：另测过 NVFP4/FP8 混合权重（每步快 1.5×），但与 DSpine 组合时 accept 从 5.02 跌到 1.37，整体反而慢约 5 倍，未采用；FP4+MTP 的 accept 为 4.46。
- **串行草稿（prompt lookup 续接草稿链）**：实现在 `eagle_worker_common.py`（默认关闭），在本次负载集上与基线持平，仅在可复制文本负载上有潜力。
- **远端出向 TCP 有 100 KiB 单连接上限**：HTTP 必须走 UDS + 桥接，但 torch 内部 TCPStore 仍走 TCP，曾导致进程组中止（非本部署代码问题）。
- **隧道为会话级**：每次重启远端服务后必须重建（客户端用 `127.0.0.1`，不要用 `localhost`——该机 localhost 优先解析 IPv6）。
